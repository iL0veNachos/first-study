Для покрытия 95%+ задач в коммерческой разработке вам не нужно заучивать всю документацию Git. Достаточно уверенно владеть базой, понимать процесс командной разработки (Gitflow/Feature Branching) и уметь исправлять частые ошибки.
Все необходимые команды делятся на 5 логических блоков:
## 1. Ежедневный рабочий цикл (Основа)
Эти команды используются по многу раз в день для создания фич и отправки кода.

* git clone <url> — клонирование репозитория на компьютер.
* git checkout -b <branch_name> (или современная git switch -c) — создание новой ветки от текущей и переход на неё.
* git status — проверка измененных и неотслеживаемых файлов.
* git add <file> (или git add . для всего) — подготовка изменений к коммиту (Staging).
* git commit -m "сообщение" — фиксация изменений.
* git push origin <branch_name> — отправка локальной ветки на удаленный сервер.

## 2. Синхронизация с командой
Используется перед началом работы и перед отправкой своего кода, чтобы избежать конфликтов.

* git fetch — скачивание информации о новых ветках и коммитах коллег с сервера (безопасно, код в ваши файлы не сливается).
* git pull — скачивание и автоматическое слияние изменений из удаленной ветки в вашу текущую.
* git switch <branch_name> — переключение между существующими ветками.

## 3. Интеграция кода и решение конфликтов
Когда ваша фича готова, или когда нужно обновить свою ветку актуальным кодом из main.

* git merge <branch_name> — слияние указанной ветки в текущую (создает коммит слияния).
* git rebase <branch_name> — перенос ваших коммитов поверх коммитов целевой ветки (делает историю линейной, очень популярен в компаниях).
* git stash — «спрятать» незакоммиченные изменения в карман, чтобы временно сделать ветку чистой (например, для срочного переключения на другую задачу).
* git stash pop — вернуть спрятанные изменения обратно.

## 4. Исправление ошибок и «разгребание» проблем
Именно за эти команды тимлиды ценят разработчиков, так как ошибки в Git случаются у всех.

* git commit --amend -m "новое сообщение" — изменение текста последнего коммита или добавление в него забытых файлов (пока не сделали push).
* git reset --soft HEAD~1 — отмена последнего коммита. Сам код остается на месте (в состоянии staged), можно переделать коммит.
* git reset --hard HEAD~1 — жесткая отмена последнего коммита. Внимание: удаляет коммит и уничтожает весь написанный в нем код.
* git revert <commit_hash> — безопасная отмена любого коммита в прошлом. Создает новый «противоположный» коммит (идеально для ветки main, где нельзя удалять историю).
* git checkout -- <file> (или git restore <file>) — отмена всех незакоммиченных изменений в конкретном файле (возврат к состоянию последнего коммита).

## 5. Анализ истории

* git log --oneline — компактный просмотр истории коммитов.
* git diff — просмотр изменений в коде, которые еще не были добавлены в коммит.
* git blame <file> — показывает построчно, кто и в каком коммите изменил этот файл (незаменимо, чтобы понять, к кому идти с вопросами по старому коду).

## Главный секрет коммерческой разработки
В 95% компаний код ревью и финальное слияние веток происходят не в консоли, а в веб-интерфейсе (GitHub, GitLab, Bitbucket) через механизм Pull Request (PR) или Merge Request (MR).
Ваш стандартный рабочий день в компании будет выглядеть так:
git switch main ➡️ git pull ➡️ git switch -c feature/my-task ➡️ (пишете код) ➡️ git add . ➡️ git commit ➡️ git push ➡️ Открытие Pull Request на сайте.
Какой из этих блоков (например, rebase против merge или отмена коммитов) вызывает у вас сейчас больше всего вопросов? Можем разобрать его механику подробно.
